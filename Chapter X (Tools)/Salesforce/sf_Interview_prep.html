Salesforce Platform Layers

  • 1Infrastructure Layer — Servers, databases, network managed by Salesforce
  • 2Platform Layer — Core CRM, object model, security engine, workflow engine
  • 3Application Layer — Sales Cloud, Service Cloud, Marketing Cloud (pre-built apps on the platform)
  • 4Custom Layer — Your org's custom objects, Apex, LWC, integrations
Platform = Force.com / Salesforce Platform. You build on Layer 4, using tools from Layers 2 & 3.

Standard Object Relationships

Lookup Relationship
  • Loosely coupled — child can exist without parent
  • Does not inherit parent OWD
  • Max 25 lookup fields per object
  • No cascade delete (by default)
  • Example: Contact lookup to Account
Master-Detail Relationship
  • Tightly coupled — child cannot exist without parent
  • Child inherits parent's OWD sharing
  • Enables Roll-Up Summary fields on parent
  • Cascade delete on parent delete
  • Max 2 master-detail per object
🎤 Interview Questions — Architecture
What is multi-tenancy? How does Salesforce isolate org data? ▼
Multi-tenancy means multiple customers share the same physical servers and database. Salesforce isolates data using an Org ID column on every table. All queries are automatically filtered by Org ID at the database level, invisible to developers. The metadata kernel stores each org's schema as data rather than separate DB schemas.
Why do Governor Limits exist? How do you handle them? ▼
Governor limits prevent any single tenant from monopolizing shared resources. To handle them: bulkify all code (never put SOQL/DML inside loops), use Collections to batch operations, use Database.QueryLocator for large datasets in Batch Apex, and query outside loops then process in-memory with Maps.
Difference between Lookup and Master-Detail relationship? ▼
Key differences: (1) Dependency — Lookup child can exist without parent, MD child cannot. (2) Sharing — MD child inherits parent OWD, Lookup does not. (3) Roll-Up — Only MD supports Roll-Up Summary fields. (4) Delete — Deleting MD parent cascades to children. (5) Limit — Max 2 MD per object, 25 lookups.
What is the difference between Force.com and Salesforce Platform? ▼
They are the same — Force.com was the original brand name, rebranded to Salesforce Platform. It is the PaaS (Platform as a Service) layer that provides the development environment (Apex, SOQL, LWC, APIs) on which all Salesforce clouds (Sales, Service, etc.) are built.
What is a Junction Object? When do you use it? ▼
A Junction Object is a custom object with two Master-Detail relationships, implementing a many-to-many relationship. Example: A Student can be enrolled in many Courses, and a Course can have many Students — an Enrollment__c junction object bridges them. Both parent MD fields are required, so the junction record is always linked to both parents.

🔐 Salesforce Security

Layered security model — object, field, and record level access control.

Security Layers: Org Access → Object Access (CRUD) → Field Access (FLS) → Record Access (OWD + Role Hierarchy + Sharing Rules)
Profiles
  • Every user must have exactly one profile
  • Controls: Object CRUD, Field FLS, App access, Tab visibility, Page Layouts, Login hours/IP
  • Acts as the baseline permission set
  • Standard profiles (System Admin, Standard User) can't be deleted
Permission Sets
  • Grant additional permissions on top of profile
  • A user can have multiple permission sets
  • More granular — can be assigned without changing profile
  • Best practice: Use minimal-access profile + permission sets
  • Permission Set Groups bundle multiple permission sets

Record-Level Security Stack

  • 1OWD (Org-Wide Defaults) — The baseline for every record. Options: Private | Public Read Only | Public Read/Write | Controlled by Parent
  • 2Role Hierarchy — Users above in hierarchy automatically get access to records owned by users below them. Upward visibility only.
  • 3Sharing Rules — Extend access beyond OWD+hierarchy. Ownership-based or Criteria-based. Cannot restrict access, only expand.
  • 4Manual Sharing — Record owner or admin manually shares individual records with users/groups.
  • 5Apex Sharing (Programmatic) — Use Account__Share objects to share records in code.
OWD Values Explained
  • Private — Only owner + above in hierarchy
  • Public Read Only — Everyone can view, only owner can edit
  • Public Read/Write — Everyone can view and edit
  • Controlled by Parent — Used in Lookup/MD relationships — inherits parent's access
  • Start with most restrictive (Private), then open up with sharing rules
Field-Level Security (FLS)
  • Controls visibility and editability per field per profile/permission set
  • 3 states: Visible + Editable, Visible + Read Only, Hidden
  • FLS respected automatically in UI
  • In Apex: use Schema.SObjectField.getDescribe() or WITH SECURITY_ENFORCED in SOQL
  • System Admin bypasses FLS

with sharing vs without sharing in Apex

Apex — Sharing Keywords
// Respects running user's sharing rules (RECOMMENDED default) public with sharing class AccountController { public List<Account> getAccounts() { // Only returns records the running user can see return [SELECT Id, Name FROM Account]; } } // Ignores sharing rules — runs in system context (use carefully) public without sharing class InternalProcessor { // Returns ALL records regardless of sharing } // Inherits sharing from the class that calls it (default if not specified) public inherited sharing class SharedHelper { }
Best Practice: Always use with sharing unless you have a specific reason not to. System Admin bypasses sharing anyway, so it only affects non-admin users.

Config Steps — Creating Sharing Rules

  • 1Go to Setup → Security → Sharing Settings
  • 2Set OWD for the object (e.g., Account = Private)
  • 3Scroll to the object's Sharing Rules section → click New
  • 4Choose Ownership-based (by record owner) or Criteria-based (by field values)
  • 5Select who to share from (roles/groups) and who to share with
  • 6Set access level: Read Only or Read/Write → Save

🎤 Interview Questions — Security
What is the difference between Profile and Permission Set? ▼
Profile: Every user has exactly one. Sets the baseline permissions (object CRUD, FLS, login hours). Cannot grant more access than available. Permission Set: Additive layer — grants extra permissions on top of profile. One user can have multiple. Modern best practice is minimal-access profile + permission sets for flexibility.
Can sharing rules restrict access? ▼
No. Sharing rules can only expand access beyond OWD. They cannot restrict it. To restrict access, you must lower the OWD or use more restrictive profiles. If you need record-level restriction below OWD, that's not possible declaratively — it requires a custom approach.
What is "with sharing" vs "without sharing" in Apex? ▼
with sharing: Apex class respects the running user's sharing rules — users only see records they have access to. without sharing: Ignores all sharing rules, runs as system. If a class doesn't declare either, it inherits the sharing context of the calling class. Always prefer with sharing unless doing background system processing where record visibility context doesn't apply.
Explain CRUD vs FLS and how to enforce them in Apex ▼
CRUD: Create, Read, Update, Delete at the object level. FLS: Field-level visibility/editability. In Apex, these are NOT automatically enforced — you must check manually. Use Schema.sObjectType.Account.isCreateable() for CRUD, Schema.sObjectType.Account.fields.Name.isUpdateable() for FLS. OR use WITH SECURITY_ENFORCED in SOQL (throws exception if FLS violated) or stripInaccessible() to remove inaccessible fields.
What are the different ways to give record access to a user? ▼
5 ways: (1) OWD — make it public. (2) Role Hierarchy — put user higher in hierarchy. (3) Sharing Rules — criteria or ownership based. (4) Manual Sharing — owner clicks Share button. (5) Apex Managed Sharing — programmatically insert Share records with custom RowCause.

Validation Rules

Validation Rules use a formula that returns TRUE to block the save. If the formula evaluates to true, the error message displays and the record is not saved.

Validation Rule Formula Examples
-- Example 1: Phone required when status is Active AND(ISPICKVAL(Status__c, "Active"), ISBLANK(Phone)) -- Example 2: Close date must be in future for new opportunities AND(ISNEW(), CloseDate < TODAY()) -- Example 3: Discount cannot exceed 20% without manager approval AND(Discount__c > 20, NOT(Manager_Approved__c)) -- Example 4: Custom email format validation AND(NOT(ISBLANK(Email__c)), NOT(REGEX(Email__c, "[a-z0-9._%+-]+@[a-z0-9.-]+\\.[a-z]{2,4}")))
Key functions: ISBLANK(), ISNEW(), ISCHANGED(), ISPICKVAL(), AND(), OR(), NOT(), REGEX(), CONTAINS(), TODAY(), NOW()

Flow — Record-Triggered Flow

  • 1Setup → Flows → New Flow → Choose "Record-Triggered Flow"
  • 2Select the Object (e.g., Opportunity), trigger: Created and/or Updated
  • 3Choose Before Save (no DML, faster, update triggering record directly) or After Save (can do DML on related records)
  • 4Add Entry Conditions to control when flow runs (e.g., Stage changed to Closed Won)
  • 5Build your logic using: Assignments, Decisions, Loops, Get Records, Create Records, Update Records, Delete Records, Subflows, Actions
  • 6✓Activate the flow — it goes live immediately

Approval Processes

Multi-step approval workflow for records. Common use case: Discount approval, Opportunity approval, Leave request.

  • 1Setup → Approval Processes → New → Choose object
  • 2Define entry criteria (when can a record be submitted?)
  • 3Set approver — User, Queue, Manager from hierarchy, or related user
  • 44Configure approval actions (field updates on submit, approve, reject, recall)
  • 5Add more steps for multi-level approval (e.g., Manager → VP → CEO)
Tip: Records are locked during approval. Approvers receive email or Chatter notifications. Can also approve via mobile.
🎤 Interview Questions — Admin
What is the difference between Before Save and After Save in Record-Triggered Flow? ▼
Before Save: Runs before the record is committed to DB. Can update the triggering record's fields directly (no DML needed — just use Assignment to set field values on {!$Record}). Faster. Cannot access record Id (not yet created). Cannot do DML on other records.

After Save: Runs after record is in DB. Can do DML on related records. Has record Id. Slower. Use After Save when you need to create/update child records.
Validation Rule vs Flow vs Apex Trigger — when do you use which? ▼
Validation Rule: Simple field-level data quality checks that block save. No business logic. Flow: Business automation that doesn't require complex coding — record updates, related record creation, sending emails, calling external services. Apex Trigger: Complex logic, multiple objects, callouts, error handling, third-party library use, or when Flow can't handle it. Prefer declarative (Flow) over code; use Apex when Flow is insufficient.
What are the Order of Execution in Salesforce? ▼
Simplified order on record save: (1) System Validation (required fields, data types). (2) Before Triggers. (3) Custom Validation Rules. (4) Duplicate Rules. (5) Record saved to DB (not committed). (6) After Triggers. (7) Assignment Rules. (8) Auto-response Rules. (9) Workflow Rules (field updates re-fire triggers). (10) Process Builder / Flows. (11) Escalation Rules. (12) Commit to DB. (13) Post-commit logic (sending emails, async queueable). Critical: Workflow field updates re-fire Before + After triggers!
What are Roll-Up Summary fields and when can't you use them? ▼
Roll-Up Summary fields on a parent object aggregate child record data: COUNT, SUM, MIN, MAX. Only available when the child has a Master-Detail relationship to the parent (not lookup). You cannot use them with Lookup relationships, cross-object (grandparent), or when the child is on the many side of a lookup. Alternative: use Flow or Apex trigger to calculate and update the parent.

Apex Trigger — Best Practice Pattern

One Trigger Per Object rule. Never put logic inside triggers. Delegate to a handler class.
Apex — Trigger + Handler Pattern
// AccountTrigger.trigger — THIN trigger, no logic here trigger AccountTrigger on Account ( before insert, before update, before delete, after insert, after update, after delete, after undelete ) { AccountTriggerHandler.handle(Trigger.new, Trigger.old, Trigger.newMap, Trigger.oldMap, Trigger.operationType); } // AccountTriggerHandler.cls — all logic here public with sharing class AccountTriggerHandler { public static void handle( List<Account> newList, List<Account> oldList, Map<Id, Account> newMap, Map<Id, Account> oldMap, System.TriggerOperation opType ) { switch on opType { when BEFORE_INSERT { onBeforeInsert(newList); } when BEFORE_UPDATE { onBeforeUpdate(newList, oldMap); } when AFTER_INSERT { onAfterInsert(newList); } when AFTER_UPDATE { onAfterUpdate(newList, oldMap); } } } private static void onBeforeInsert(List<Account> newList) { // Bulkified: loop over list, not individual records for (Account acc : newList) { if (acc.Industry == null) acc.Industry = 'Technology'; } } private static void onAfterInsert(List<Account> newList) { // Create related Contact after Account created List<Contact> contacts = new List<Contact>(); for (Account acc : newList) { contacts.add(new Contact( LastName = acc.Name + ' Contact', AccountId = acc.Id )); } if (!contacts.isEmpty()) insert contacts; } }

SOQL & SOSL

SOQL — Salesforce Object Query Language
// Basic query [SELECT Id, Name, Industry FROM Account WHERE Industry = 'Technology' ORDER BY Name LIMIT 100]; // Relationship query (child-to-parent) [SELECT Id, Name, Account.Name FROM Contact WHERE Account.Industry = 'Tech']; // Parent-to-child subquery [SELECT Id, Name, (SELECT Id, LastName FROM Contacts) FROM Account]; // Aggregate query [SELECT Industry, COUNT(Id) FROM Account GROUP BY Industry]; // WITH SECURITY_ENFORCED (FLS check) [SELECT Id, Name FROM Account WITH SECURITY_ENFORCED];
SOSL — Salesforce Object Search Language
// Search across multiple objects at once FIND {'Acme'} IN ALL FIELDS RETURNING Account(Id, Name), Contact(Id, FirstName, LastName), Lead(Id, Name); // Search specific field groups FIND {'John*'} IN NAME FIELDS RETURNING Contact(Id, Name WHERE AccountId != null); // In Apex List<List<SObject>> results = [FIND :searchTerm IN ALL FIELDS RETURNING Account(Id, Name)]; List<Account> accounts = (List<Account>) results[0];
SOQL = specific object, structured. SOSL = full-text search across multiple objects simultaneously.

Run single method async. No chaining. Accepts primitive params only. Good for simple callouts.

🎤 Interview Questions — Development
What is trigger bulkification and why is it important? ▼
Triggers fire for batches of records (e.g., data loader uploading 10,000 records). If you put SOQL inside a loop, you'll hit the 100 SOQL limit fast. Bulkification means: collect all record IDs → query once outside loop → store in Map → use Map inside loop. Example: Map<Id, Account> accMap = new Map<Id, Account>([SELECT Id FROM Account WHERE Id IN :accountIds]);
When would you use Queueable vs Batch Apex vs @future? ▼
@future: Simple one-off async, callouts from triggers, primitive params only. Queueable: More complex async, need to chain jobs, pass non-primitive params (SObjects), need job ID for monitoring. Batch: Processing huge volumes of records (>50k), need per-chunk governor limits reset, need stateful counter across chunks. Rule: use the simplest tool that fits.
Difference between @wire and imperative Apex call in LWC? ▼
@wire: Reactive — automatically calls the Apex method when reactive properties (like $recordId) change. Data is cached by Salesforce. Runs on component load. Good for read-only data that should refresh reactively. Imperative: You call the method explicitly (e.g., on button click). Returns a Promise. More control — can pass dynamic params, trigger on events, handle complex error scenarios. Not cached by default.
What is Database.SaveResult and why use Database.insert vs insert? ▼
insert myList; — throws exception on first failure, entire transaction rolls back. Database.insert(myList, false); — partial success allowed (allOrNone = false). Returns Database.SaveResult[] where you can check each record's success/error: if (!result.isSuccess()) { result.getErrors()... }. Use Database.insert when you want to process valid records even if some fail — common in batch processing.
What is ISCHANGED() and how do you check if a field changed in a trigger? ▼
In a trigger: Trigger.oldMap.get(acc.Id).Status__c != acc.Status__c — compare old value to new. ISCHANGED() is the formula equivalent for Workflow/Flow/Validation Rules. In triggers always use Trigger.oldMap (available in update/delete contexts). Always null-check: if (Trigger.isUpdate && oldMap.get(rec.Id).Field__c != rec.Field__c)

Apex Callouts — Salesforce calling External

Apex — REST Callout with Named Credential
public class ExternalAPIService { // Must be @future(callout=true) if called from trigger public static String getWeatherData(String city) { // Named Credential handles auth — no hardcoded credentials! HttpRequest req = new HttpRequest(); req.setEndpoint('callout:Weather_API/current?city=' + city); req.setMethod('GET'); req.setTimeout(10000); // 10 seconds max Http http = new Http(); HttpResponse res = http.send(req); if (res.getStatusCode() == 200) { Map<String, Object> body = (Map<String, Object>) JSON.deserializeUntyped(res.getBody()); return (String) body.get('temperature'); } else { throw new CalloutException( 'Callout failed: ' + res.getStatus()); } } }
Important: You cannot make callouts in the same transaction as DML (you'll get a "uncommitted work pending" error). Use @future(callout=true) or Queueable with Database.AllowCallouts.

Platform Events — Event-Driven Architecture

Platform Events are Salesforce's pub/sub messaging. Decouples systems — publisher doesn't need to know about subscribers.

Platform Events — Publish from Apex
// 1. Create Platform Event object: Order_Event__e (via Setup) // 2. Publish from Apex public class OrderEventPublisher { public static void publishOrderCreated(Id orderId, String status) { Order_Event__e event = new Order_Event__e( Order_Id__c = orderId, Status__c = status, Timestamp__c = DateTime.now() ); Database.SaveResult result = EventBus.publish(event); if (!result.isSuccess()) { System.debug('Event publish failed: ' + result.getErrors()); } } } // 3. Subscribe via Trigger on the Platform Event trigger OrderEventTrigger on Order_Event__e (after insert) { for (Order_Event__e event : Trigger.new) { System.debug('Order received: ' + event.Order_Id__c); // Process order — update records, send notifications, etc. } }
Platform Events vs Change Data Capture (CDC): Platform Events are custom events you define. CDC automatically publishes events when standard/custom objects change — useful for syncing external systems.

🎤 Interview Questions — Integration
What are Named Credentials and why use them over hardcoding URLs? ▼
Named Credentials store external endpoint URLs and authentication details (API keys, OAuth tokens) securely in Salesforce — not in code. Benefits: (1) No credentials in source code or Custom Settings that can be exported. (2) Auth token refresh handled automatically for OAuth. (3) Remote Site Settings not needed separately. (4) Per-User identity possible — each user's credentials used for their requests. Hardcoding credentials is a security anti-pattern that fails code reviews.
What is the difference between Platform Events and Streaming API / PushTopic? ▼
PushTopic/Streaming API: Subscribe to SOQL query results and receive notifications when matching records change. Older approach. Platform Events: Custom event objects you define. Fully decoupled pub/sub. Events are durable (retained 72 hours). More scalable. Platform Events are the modern recommended approach — Salesforce is deprecating PushTopics in favor of Change Data Capture + Platform Events.
How do you handle callouts in a trigger context? ▼
You cannot make synchronous callouts directly in a trigger (DML + callout in same transaction is not allowed). Solutions: (1) Use @future(callout=true) method — pass primitive params from trigger to @future. (2) Use Queueable Apex implementing Database.AllowsCallouts. (3) Use Platform Events to decouple — trigger publishes event, subscriber makes callout.
What OAuth flows does Salesforce support? Which is used when? ▼
Web Server Flow: Server-side web apps, most common, uses auth code + redirect URI. User-Agent Flow: Client-side JS apps, implicit grant. Username-Password Flow: Server-to-server (no user interaction), used for backend integrations. JWT Bearer Flow: Server-to-server with certificate, no user credentials in code. Device Flow: IoT/CLI apps with limited input. Refresh Token Flow: Renewing access without re-auth. For 2 YOE: know Web Server and Username-Password well.

Smoke Testing — Post-Deployment Checklist

Quick sanity checks immediately after deploying to any environment. Not exhaustive — just verifies nothing is catastrophically broken.

  • Core navigation: Can users log in? Does the home page load? Do tabs open?
  • Critical object CRUD: Can you create an Account, Contact, Opportunity? Do record pages load?
  • Key flows: Does the primary sales/service workflow work end-to-end?
  • Integrations live: Are API callouts to external systems responding?
  • Deployed changes: Verify the specific features that were deployed work as expected
  • No critical errors: Check Debug Logs and Platform Events for error spikes
Duration: 15-30 minutes. Smoke testing should be fast. If it takes hours, that's System Testing territory.

UAT — User Acceptance Testing

  • 1Define Acceptance Criteria — from user stories/business requirements. Clear pass/fail conditions.
  • 2Create Test Scripts — step-by-step scenarios for business users to follow, with expected results.
  • 3Prepare Test Environment — use a Full Sandbox with representative production data.
  • 44Business Users Execute Tests — actual end users (not developers) run scenarios.
  • 5Log Defects — anything that doesn't match expected behavior is raised as a defect (not a change request).
  • 6Sign-off — stakeholders formally approve go-live once all critical defects resolved.
Common UAT Issues in Salesforce: Data not carrying over from old system, sharing rules restricting access for test users, email alerts going to wrong recipients, page layouts missing expected fields.

Regression Testing

After any change, ensure existing functionality is not broken. In Salesforce context:

  • Run all Apex tests — Run All Tests in Developer Console or CI pipeline
  • Validation rules — test edge cases that were previously passing
  • Integrations — re-test all API endpoints after field/object changes
  • Reports/Dashboards — verify data still aggregates correctly after schema changes
  • Automation — re-test all Flows and triggers affected by changed objects
  • Page Layouts — verify all profiles see the correct layout after changes
Regression Test Suites: In Salesforce, create Test Suites (Developer Console → Test → New Suite) to group related test classes and run them together in CI/CD pipelines.

Performance Testing in Salesforce

  • Data Volume Testing: Test with production-like data volumes. A query that works on 100 records may time out on 100,000.
  • Governor Limit Testing: Use Limits.getQueries(), Limits.getCpuTime() in debug logs to profile real usage.
  • Batch size testing: Test Batch Apex with chunk sizes 200 (default), 100, and 50 to find optimal size.
  • Load testing: Use Salesforce Bulk API to test insert/update of large datasets. Use Real-Time Event Monitoring.
  • Page performance: Use Salesforce Lightning Inspector (Chrome extension) to analyze LWC rendering performance.
🎤 Interview Questions — Testing
What is the Salesforce code coverage requirement? What counts as covered? ▼
Minimum 75% code coverage across all Apex in the org (not per class) is required to deploy to production. A line is "covered" if a test method executes it. Comments, blank lines, and System.debug() don't count. Test classes themselves don't count. Important: Coverage is necessary but not sufficient — also assert correct behavior, not just execute lines.
What is Test.startTest() / stopTest() and why is it important? ▼
Test.startTest() resets all governor limit counters — so limits used in @TestSetup don't count against your test's limits. Test.stopTest() forces all asynchronous operations (future, queueable, batch, scheduled) to complete synchronously within the test. This is how you test async code — start, call async method, stopTest, then assert on results.
What is the difference between Unit Testing and Integration Testing in Salesforce? ▼
Unit Testing: Tests a single Apex method in isolation. External dependencies (callouts, other systems) are mocked using HttpCalloutMock or Test.setMock(). Fast, no external dependencies, runs every deployment. Integration Testing: Tests the actual interaction between Salesforce and external systems. Uses real endpoints (in a sandbox). Verifies data actually flows correctly. Done less frequently — usually pre-deployment or on-demand.
What is a Full Sandbox vs Partial vs Developer Sandbox? ▼
Developer: No production data, metadata only, 200MB storage, free, fast refresh. Good for development. Developer Pro: Like Developer but 1GB storage. Partial: Metadata + sample production data (up to 5GB), 5-day refresh. Good for UAT with realistic data. Full: Complete copy of production (metadata + all data), refresh once every 29 days, matches production storage. Used for UAT, performance testing, regression. Choose environment based on how representative data needs to be.

🎛 Salesforce Configuration

Clicks not code — custom objects, fields, layouts, and App Builder.

Custom Object & Field Creation

  • 1Setup → Object Manager → Create → Custom Object
  • 2Enter Label (singular), Plural Label, Object Name (API name gets __c suffix automatically)
  • 3Choose Record Name type: Text (auto-number) or Auto Number
  • 4Enable optional features: Allow Chatter Feed, Track Field History, Reports, Search
  • 5After saving: Add Custom Fields → Choose field type → Set label → Configure FLS → Add to Layout

Field Types — Know Them All

Data Fields
  • Text — up to 255 chars, indexed if unique
  • Text Area — up to 255 chars, not searchable
  • Long Text Area — up to 131,072 chars
  • Rich Text — HTML formatted, up to 131,072
  • Number — decimals configurable
  • Currency — respects org currency settings
  • Percent — number stored as decimal
  • Date / DateTime — timezone aware for DateTime
  • Checkbox — boolean, default true/false
  • Email — validated email format
  • Phone — free text, click-to-dial
  • URL — clickable hyperlink
  • Picklist — single select from list
  • Multi-Select Picklist — multiple values, stored semicolon-delimited
Calculated / Relationship
  • Formula — read-only calculated, not stored in DB
  • Roll-Up Summary — aggregate child records (MD only)
  • Lookup — link to another object (loose coupling)
  • Master-Detail — tight coupling with cascade delete
  • Hierarchy — self-lookup (used in User object)
  • External Lookup — link to external object
Special
  • Geolocation — lat/lng coordinate pair
  • Encrypted Text — stored encrypted (Shield)
  • Auto Number — auto-incrementing with prefix
Multi-Select Picklist in SOQL: Use INCLUDES() instead of = : WHERE Category__c INCLUDES ('Tech')

🎤 Interview Questions — Configuration
What is the difference between a Formula field and a Roll-Up Summary field? ▼
Formula Field: Calculated on-the-fly when record is displayed. References fields on the same record or parent (via lookup/MD). Not stored in DB. Can cross-reference parent records. Available on all objects. Roll-Up Summary: Stored in DB, calculated when child records change. Only on parent in Master-Detail. Aggregates child record data (COUNT, SUM, MIN, MAX). Can have filter criteria. Slower to calculate but stored value available for indexing/reporting.
How do you migrate configuration between environments? ▼
Three main approaches: (1) Change Sets — GUI-driven, simple deployment of metadata between connected orgs. Good for small changes. (2) Salesforce CLI (SFDX) — retrieve metadata as files, deploy via CLI commands. Works with any org. CI/CD friendly. (3) ANT Migration Tool — older, XML-based. Being phased out. Modern projects use SFDX + source control (Git) + CI/CD (GitHub Actions, Jenkins, Copado).
What is a Page Layout vs a Lightning Record Page? ▼
Page Layout (Classic): Controls which fields, related lists, and buttons appear on a record. Assigned by Profile + Record Type. Part of Classic and Lightning. Lightning Record Page (App Builder): Controls the overall page structure in Lightning — which components appear, where, with what configuration. Can embed multiple page layouts in different sections. Assigned by Profile, App, or Record Type. Lightning Record Pages are more flexible — they can show LWC components, related apps, etc. that Classic Page Layouts cannot.

📊 Reports & Dashboards

Building insights from Salesforce data — report types, formats, and dashboard design.

Report Types — Know the 4 Formats

Tabular Report
  • Simple list of records — like a spreadsheet
  • No subtotals, no grouping
  • Cannot be used as dashboard source (unless with row limit)
  • Good for: export lists, simple record inventories
Summary Report
  • Records grouped by rows with subtotals
  • Can add up to 3 levels of grouping
  • Most common type for dashboards
  • Good for: Opportunities by Stage, Accounts by Industry
Matrix Report
  • Grouped by BOTH rows AND columns
  • Shows data in grid format with subtotals on each axis
  • Good for: Sales by Rep by Month, Leads by Source by Region
Joined Report
  • Multiple report "blocks" — each block can use a different report type
  • Compare data across different objects in one report
  • Good for: Accounts with open Opps + Accounts with open Cases
  • Cannot be used as dashboard source

Report Builder — Key Features

Filters
  • Standard Filter — date range, owner, record type
  • Field Filter — filter by any field value
  • Cross Filter — "Accounts WITH Opportunities" or "WITHOUT"
  • Row Limit — for Tabular reports (required for dashboard use)
  • Filter Logic — AND/OR combinations: 1 AND (2 OR 3)
Advanced Features
  • Bucket Column — group picklist/number/text values into buckets without formula
  • Summary Formula — custom calculations (% of total, ratio)
  • Conditional Highlighting — color cells based on value thresholds
  • Report Subscriptions — auto-email report on schedule
  • Historical Trending — track field value changes over time

Custom Report Types

Standard report types cover most standard objects. Custom Report Types let you create reports spanning custom objects or relationships not available by default.

  • 1Setup → Report Types → New Custom Report Type
  • 2Choose the Primary Object (e.g., Account)
  • 3Add related objects — "with" (inner join) or "with or without" (left outer join)
  • 4Deploy the report type and add it to a category
  • 5Add available fields to the field layout — users building reports see only these fields
Tip: "With" means only records that HAVE the related object (inner join). "With or without" means all primary records, even if no related records exist (left join).

Dashboards

Dashboard Components
  • Chart — bar, line, pie, donut, funnel, scatter, gauge
  • Table — tabular data from report
  • Metric — single number (total, count)
  • Gauge — progress toward target (red/yellow/green ranges)
  • Visualforce page — embed custom VF content
  • Custom LWC — embed Lightning components
Limits & Behavior
  • Max 20 components per dashboard
  • Dashboard Running User — whose data/sharing the dashboard uses
  • Dynamic Dashboard — runs as the logged-in user (each user sees their data)
  • Max 5 dynamic dashboards per org (Enterprise) or 10 (Unlimited)
  • Dashboards refresh on demand or scheduled
  • Can be embedded in record pages via App Builder

Dynamic Dashboards — Implementation

  • 1Create reports with "My" filters (My Accounts, My Opportunities) so they scope to the viewing user
  • 2Create a new Dashboard → in Properties, set Running User to "Run as logged-in user"
  • 3Add components from the "My" scoped reports
  • 4Each sales rep viewing the dashboard sees only their own data
Limitation: Dynamic Dashboard data is not cached per-user — each view is a fresh query. Refreshing a dynamic dashboard refreshes it for you only, not other users.
🎤 Interview Questions — Reports & Dashboards
What are the 4 report types? When would you use each? ▼
Tabular: Simple list, no grouping. Export data, quick record lists. Cannot be dashboard source without row limit. Summary: Grouped rows with subtotals. Most common — sales pipeline by stage, leads by source. Best for dashboards. Matrix: Rows AND columns grouping. Comparing same metric across two dimensions — rep performance by quarter. Joined: Multiple blocks, multiple report types in one. Compare accounts with/without opportunities in same view.
What is a Dynamic Dashboard? Limitations? ▼
A Dynamic Dashboard runs as the logged-in user rather than a fixed running user. Each viewer sees data they have access to. Ideal for sales reps each seeing their own pipeline. Limitations: (1) Max 5 per org in Enterprise, 10 in Unlimited. (2) Cannot schedule dynamic dashboards. (3) Cannot be subscribed to. (4) The viewing user must have access to the underlying reports. (5) No data caching across users.
What is a Bucket Column in a report? ▼
Bucket Columns let you categorize report data without creating a formula field. Example: ACV Amount — bucket "Small" (<$10k), "Medium" ($10k-$100k), "Large" (>$100k). Supports Text (map specific values to buckets), Number (define ranges), and Picklist fields. Good for ad-hoc grouping in reports without changing the data model. Formula fields are better when you need the calculation across the whole org.
A user says their dashboard shows wrong data. How do you investigate? ▼
Step by step: (1) Check the Running User of the dashboard — is it a specific user or "as logged-in user"? (2) Open the underlying report — does it show the right data? (3) Check report filters — is the date range, owner filter, or record type filter excluding the expected data? (4) Check the sharing/OWD of the running user — can they see those records? (5) Check when the dashboard was last refreshed — stale data? (6) Check if Field Filters or Cross Filters are too restrictive.
